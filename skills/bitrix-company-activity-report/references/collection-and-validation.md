# Сбор источников и контроль полноты

Памятка для реализации отчёта; это не гарантия, что каждый метод доступен любому вебхуку. Проверяй разрешения и текущую схему ответа доступными read-only методами. Не устанавливай интеграции ради обхода ограничения.

## Минимальная модель

- Параметры: `employee_id`, подтверждённое имя, начало/конец периода, timezone, время выгрузки и проверки ответственных.
- Компании: ID, название, текущий ответственный, ссылка. Индекс контактов и сделок содержит только ID и необходимые CRM-связи.
- Нормализованное событие: собственный ID, source IDs, company ID, автор и основание авторства, timestamp с зоной, тип, направление, флаг включения в исходящие, исход звонка, подтверждённая длительность, канал, инициатива, доступные тема/текст, CRM-ссылка.
- Полнота каждого источника: метод, фильтры, пагинация/число страниц, время проверки, ошибки, исключённые/нераспределённые записи и причина. Секреты не журналировать. Факт отсутствия ошибок не означает полноту неподдерживаемого источника.

## CRM-связи

`crm.company.list` позволяет отобрать компании по ответственному. Контакты читать с основной компанией и при необходимости доступными дополнительными связями. Если фактическая связь в UI отличается от одиночного COMPANY_ID, нужно проверить доступные REST-связи, а не выводить контакт отдельной строкой или угадывать компанию. Для событий с несколькими bindings проверять реальные owner/company/contact/deal ID.

У `crm.activity.list` вложенный фильтр BINDINGS может вернуть неожиданно широкую выборку. Не доверять одному успешному ответу: проверять привязку каждой включённой записи, а сомнительных кандидатов дочитывать индивидуально. Сделки использовать для связи комментария/дела с компанией, а не автоматически включать все действия по сделке.

## Источники

- Звонки: `voximplant.statistic.get` и CRM-дела (`crm.activity.get/list`). Сопоставляй один реальный звонок с его CRM-делом; не складывай эти источники как два касания. Установи направление, сотрудника, исход и длительность по фактическим полям.
- Письма и другие дела: `crm.activity.list/get`; проверь тип/provider, факт отправки и исполнителя. Фильтр CREATED сам по себе не покрывает события, созданные раньше, но выполненные в периоде. Сканирование по нескольким релевантным датам требует дедупликации и окончательной проверки времени фактического действия.
- Комментарии: `crm.timeline.comment.list` по компаниям, их контактам и связанным сделкам; проверяй автора и дату каждого комментария. Автор зеркального дела/задачи не доказывает отдельное касание.
- Переписка: доступные read-only методы открытых линий, например `imopenlines.crm.chat.get`, и чтение сообщений через `im.dialog.messages.get`, если разрешено. Одинаковый чат у компании и её контакта читать/считать один раз. Метаданные коннектора могут находиться в uppercase-полях `ATTACH`, `FILE_ID`, `COMPONENT_ID`, `CLASS`; технические системные сообщения исключать.
- Whazzup: в известном формате явный заголовок содержит «Исходящее сообщение, автор: Битрикс24 (Имя сотрудника)». Проверяй конкретное выбранное имя/ID, а не имя из прошлой задачи. При совпадении имён неоднозначность не скрывать. Входящее сообщение клиента не приписывать техническому отправителю как действию сотрудника.
- Массовая кампания: отдельный доступный источник отправок и подтверждение участия сотрудника. Без него «рассылка не подтверждена», даже если много одинаковых текстов. Не пытаться восстановить кампанию по похожести сообщений.

## Пагинация и временные границы

Читай все страницы и сверяй итог с total, если API его предоставляет. Для больших наборов используй разрешённые read-only batch, небольшие контролируемые пакеты, обработку лимитов и сохранение прогресса. Не запускай повторно завершённые выгрузки без причины.

Для чатов читай назад до начала периода; можно сохранить одну предшествующую граничную запись для контекста инициативы. Остановка по дате допустима только при подтверждённом порядке; системный перезапуск/новая сессия может обрывать контекст. При неполной истории инициатива неизвестна, а не автоматически исходящая. Не загружай все старые переписки в контекст модели: сначала фильтруй и нормализуй локально.

При смене списка компаний старая выгрузка может не покрывать новые компании/контакты. Дочитай недостающую область либо обозначь неполноту; одной фильтрации старого JSON для новых ID недостаточно. При неизменном списке и согласованной пересборке можно переиспользовать исходные события, сообщив дату их выгрузки.

## Проверки, предотвращающие реальные ошибки

1. Сумма исходящих по типам равна общему итогу. Все исходящие приписаны выбранному сотруднику по доказательствам; компании имеют нужного ответственного. Входящие — отдельный поток компаний.
2. Счётчик звонков включает **все три исхода**: разговор + попытка + неизвестно. Не терять неизвестный исход в кликабельном числе или сортировке; раскрытие должно содержать столько же звонков, сколько показано.
3. Диалоги объединены по company ID + локальному дню, отдельно для исходящих и входящих. После смены группировки пересчитать, а не суммировать прежние дневные счётчики контактов.
4. Из HTML извлечь встроенный JSON и сравнить с итоговыми данными; проверить синтаксис JS, экранирование источников, разрешённые CRM-host/href, отсутствие секретных REST URL и внешних ресурсов.
5. В локальном браузере сравнить «Все», каждый доступный тип и выбранную компанию с независимым расчётом. Типовой сценарий: найти компанию → выбрать звонки → нажать число → сверить количество записей и ID ссылок → сбросить. Проверить сортировку в обе стороны, отсутствие результатов и все компании с нулевыми строками.
6. CSV: реальная загрузка, число компаний и суммы соответствуют фильтру; кириллица и разделители читаются; неизвестные значения не превращаются в ноль.

Не создавать копию сырых источников в публичном шаблоне навыка. В навык входят алгоритм и технические инварианты; персональные данные конкретного отчёта остаются в его локальной папке.
